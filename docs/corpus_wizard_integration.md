# Corpus Wizard Integration Documentation

## Overview

The corpus wizard integration has been enhanced to fix critical issues that prevented newly built corpora from functioning correctly. This document describes the fixes implemented and how the integrated system works.

## Fixed Issues

### 1. Filter System Integration

**Problem**: Filters were not appearing in the UI after corpus activation.

**Root Cause**: The generated retriever could not read the manifest structure correctly. The `get_corpus_options()` method was looking for filter values in the wrong location.

**Solution**: Updated the retriever template to correctly read from `manifest.fields.corpus.values`:

```python
# Try new manifest structure first (fields.corpus.values)
if "fields" in self.manifest and "corpus" in self.manifest["fields"]:
    corpus_field = self.manifest["fields"]["corpus"]
    if "values" in corpus_field:
        for value in corpus_field["values"]:
            # Create human-readable labels
            label = value.replace("_", " ").title()
            options.append({"value": value, "label": label})
```

### 2. Target Configuration

**Problem**: Queries failed with "Unknown error" due to missing target configuration.

**Root Cause**: No target configuration file was generated during corpus activation, breaking the unified configuration system required for query execution and telemetry tracking.

**Solution**:
- Added a Target Configuration step to the wizard UI
- Users can now configure LLM provider, model, and search parameters
- Target configuration files are automatically generated during activation
- The TEST_TARGET environment variable is updated to point to the new target

### 3. Environment Variables

**Problem**: The VITE_SITE_TITLE was not updated when activating a corpus.

**Root Cause**: The activation process did not update environment variables.

**Solution**: The activation endpoint now updates both TEST_TARGET and VITE_SITE_TITLE in all environment files:

```python
# Update VITE_SITE_TITLE with corpus display name
display_name = request.get('display_name', corpus_name)
for env_file in env_files:
    # Update VITE_SITE_TITLE line
    lines[i] = f'VITE_SITE_TITLE={display_name}\n'
```

## New Features

### Target Configuration UI

The wizard now includes a dedicated step for configuring test targets:

- **LLM Provider**: Select from Anthropic, OpenAI, Google, Bedrock, or Ollama
- **Model**: Specify the model to use (e.g., claude-3-5-haiku-20241022)
- **Search Parameters**: Configure search_k, search_type, score_threshold
- **Advanced Settings**: Optional temperature and max_tokens configuration

### Unified Configuration Display

Before activation, users see a complete configuration review showing:

- **Corpus Settings**: Name, collection, embedding model, documents, filters
- **Target Settings**: Provider, model, search parameters
- **Generated Files**: Target name, retriever name, site title

This ensures transparency and allows users to verify all settings before activation.

## Unified Configuration System

The unified configuration system is critical for telemetry and system operation:

```javascript
unified_config = {
    corpus_settings: {
        name: "corpus_name",
        collection_name: "corpus_collection",
        embedding_model: "model_id",
        chunk_size: 1000,
        chunk_overlap: 200,
        total_documents: 100,
        filters: ["filter1", "filter2"]
    },
    target_settings: {
        provider: "anthropic",
        model: "claude-3-5-haiku",
        search_k: 20,
        search_type: "similarity",
        score_threshold: 0.7
    },
    composite_target: "k20_claude_corpus_collection"
}
```

### Telemetry Impact

The unified configuration ensures all fields are available for Phoenix telemetry:

- `composite_target`: Unique identifier for tracking
- All corpus settings for performance analysis
- Target settings for LLM usage tracking
- Complete configuration for debugging and optimization

## Environment Migration

A migration script is provided to clean up obsolete environment variables:

```bash
# Dry run to see what would be removed
python scripts/migrate_env_cleanup.py --dry-run

# Run the actual migration
python scripts/migrate_env_cleanup.py
```

The script removes deprecated variables such as:
- HANSARD_SOURCES_ROOT
- MULTI_CORPUS_* variables
- CHROMA_* variables (now in corpus config)
- BM25_CORPUS
- RETRIEVER_MODULE (now auto-detected)

## File Generation

During corpus activation, the following files are generated:

### Target Configuration File
Location: `backend/targets/k{search_k}_{model}.txt`
```
# Target configuration generated by Corpus Wizard
# Created: 2024-01-29T10:00:00
# Corpus: my_corpus

LLM_PROVIDER=anthropic
LLM_MODEL=claude-3-5-haiku-20241022
SEARCH_K=20
SEARCH_TYPE=similarity
SCORE_THRESHOLD=0.7
TEMPERATURE=0.7
MAX_TOKENS=4096
```

### Updated Environment Files
All `.env` files are updated with:
- `TEST_TARGET`: Points to the generated target configuration
- `VITE_SITE_TITLE`: Set to the corpus display name

## Usage

1. **Build a corpus** through the wizard
2. **Configure target settings** in the new Target Config step
3. **Review configuration** in the unified display
4. **Activate the corpus** - all configurations are applied automatically
5. **Restart the server** to use the new corpus

The corpus is now fully integrated with:
- Filters appearing in the UI
- Queries executing successfully
- Correct site title displayed
- Complete telemetry tracking
